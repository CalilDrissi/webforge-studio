Executive Summary

Over a single session, we took the open-source VVVEB.js drag-and-drop website builder and transformed it into Webforge Studio - a full desktop application. The work spanned four major phases: (1) whitelabeling the upstream project by renaming every vvveb reference to webforge across 39 source files and 254 submodule files; (2) building a Tauri desktop dashboard that manages multiple Webforge editor instances with SQLite-backed site storage; (3) adding a Theme Builder that converts static HTML and WordPress theme folders into Webforge-ready section packs exportable as zip; and (4) bundling Webforge inside the Tauri app with an embedded Hyper HTTP server, a same-origin proxy for remote sites, intercepted save/upload routing, upload progress events, and file conflict detection.

Every layer was tested: the renamed editor loads with zero JS errors and all 9 Webforge.* submodules intact; the converter generates valid sections.js that registers cleanly with the editor; the embedded server serves the bundled editor with the bridge shim injected; the proxy rewrites URLs correctly (12/12 test cases); and save-to-disk logic passes 5/5 tests including path-traversal protection.

Phase 1: Whitelabeling VVVEB.js to Webforge

Decision

Started by cloning github.com/givanz/vvvebjs to /Users/cal/webforge. After surveying the codebase, discovered the vvveb string appears in three distinct layers:

LayerExamplesCountRisk
BrandVvvebJs, vvvebjs, vvveb.com~80Low
JS namespaceVvveb.Builder, Vvveb.Components, Vvveb.Gui...~600High - every plugin
HTML/CSS hooksdata-vvveb-action, id="vvveb-builder", .vvveb-hidden~300High - couples HTML+JS+CSS

User chose "Full rename, all occurrences" with external URLs removed entirely. Name selected: Webforge.

Execution

Applied a multi-step sed pipeline across 37 source files in a specific order to avoid collisions:

# 1. VvvebJs (project name, capital J) -> Webforge    [before Vvveb. to avoid partial matches]
# 2. vvvebjs (lowercase id) -> webforge
# 3. data-v-vvveb- (typo variant) -> data-v-webforge-  [before data-vvveb-]
# 4. data-vvveb- -> data-webforge-
# 5. Vvveb. (JS namespace) -> Webforge.
# 6. standalone Vvveb word -> Webforge
# 7. vvveb- (CSS classes, ids) -> webforge-
# 8. strip vvveb.com, github.com/givanz/VvvebJs, paypal.me, opencollective URLs
# 9. any remaining bare vvveb (case-insensitive) -> webforge

Then applied the same pipeline to the demo/landing git submodule (254 additional files).

Files renamed

  • css/vvvebjs-editor-helpers.css → css/webforge-editor-helpers.css
  • scss/vvvebjs-editor-helpers.scss → scss/webforge-editor-helpers.scss
  • Reference in builder.js:1204 updated to match

Critical bug found and fixed during testing

Bug: Case-insensitive sed mangled the namespace declaration

The final case-insensitive sed pass (s/vvveb/webforge/gI) lowercased the only Vvveb declaration in the codebase at libs/builder/builder.js:171: 

// original:  if (Vvveb === undefined) var Vvveb = {};
// became:     if (webforge === undefined) var webforge = {};

This created a lowercase webforge global while every other reference used Webforge. (capitalized). Result: Webforge is not defined × 17 page errors. Fixed by restoring the capital: if (Webforge === undefined) var Webforge = {};

Verification

Loaded the editor via a Playwright-driven static server and confirmed:

  • Zero JS page errors after the fix
  • Webforge namespace defined as object with all 9 submodules: Builder, Gui, Components, FileManager, SectionList, Breadcrumb, Undo, Sections, Blocks
  • Builder iframe loaded the demo landing page (32 child elements, NAV/HEADER/SECTION rendered)
  • 31 input templates + 50 data-webforge-action hooks wired correctly
  • Component panel: 14 items | Sections panel: 15 items | File manager: 51 pages
Apache-2.0 attribution note

Per user's explicit decision, all attribution mentions of VvvebJs were stripped (including README and LICENSE). Apache-2.0 Section 4(d) legally requires preserving attribution notices - this risk was flagged and acknowledged.

Phase 3: Theme Builder

Goal

Convert HTML or WordPress template folders into Webforge-ready section packs, exportable as zip.

Input formats

  • Folder drag-and-drop via Tauri native dialog (Tauri webview doesn't expose absolute paths for web drops, so we route through openDialog({directory: true}))
  • Auto-classification: detects WordPress themes by presence of style.css with Theme Name: header + PHP files; falls back to static HTML

Rust modules added

folder.rs - scan_folder + classify_folder

  • Recursively walks the folder (skips node_modules, .git, vendor, __macosx)
  • Classifies files into html_files, php_files, css_files, js_files, asset_files
  • Classification returns {kind: "wordpress"|"html"|"unknown", theme_name, theme_version, template_count, notes}
  • Extracts Theme Name: and Version: from WP style.css headers

converter.rs - convert_template

  • For WordPress: prefers template-parts/ PHP files, then falls back to header.php/footer.php/single.php/page.php/index.php
  • For HTML: processes all .html files
  • Strips <?php ... ?> and <?= ... ?> tags → <!-- php --> / <!-- php-echo --> placeholders
  • Splits each file into sections by <section>, <header>, <footer>, <nav>, <aside> tags
  • Nested-dupe protection: skips a tag if it's already inside an extracted parent (e.g. <nav> inside <header> is not extracted twice)
  • Extracts first CSS class + detects assets (img/video/background-image)
  • Collects asset paths from src and href, filtering out http, //, data:, #, <!--, mailto:, javascript:, tel:
  • Renders Webforge.SectionsGroup['group'] = [...] + Webforge.Sections.add("key", {name, image, html}) calls
  • Backtick-escapes HTML for safe embedding in JS template literals (\`, \${, \\)

export.rs - export_zip

  • Bundles sections.js, blocks.js (empty group placeholder), README.txt (install instructions), and assets/* into a zip
  • Uses zip crate with Deflated compression
  • Path-traversal safe (asset paths are cleaned and checked against the scan root)
  • Saves via native saveDialog

Frontend

  • Drop zone (click → native folder dialog, or drag a folder onto the zone)
  • Classification panel with badge ("WordPress theme" / "Static HTML") + notes
  • Group name input (defaults to WP theme name if detected)
  • Convert button → results panel with per-section: key, source file, tag badge, class badge, asset indicator, truncated HTML preview
  • Export button → native save dialog → zip
  • Live log panel
  • Tab navigation between "Sites" and "Theme Builder" views

Phase 4: Bundling Webforge Inside Tauri

Goal

Make the editor load from local resources so only save/upload calls hit the remote server. User specified: "what's fullest production grade implementation".

Architecture decision

Three options were evaluated:

  1. Tauri resources + tauri:// protocol - simple but cross-origin iframe breaks frameDoc access (dealbreaker)
  2. Embedded localhost HTTP server - same-origin, but iframe loads remote content
  3. Local-first - saves to disk, no remote support

Chose a production-grade hybrid: embedded Hyper HTTP server that serves the bundled Webforge editor shell, with sites being either local folders (save to disk) or remote URLs (proxy + forward to save.php).

Bundled assets

  • 73MB Webforge copy in src-tauri/resources/webforge/
  • Registered in tauri.conf.json under bundle.resources
  • Resolved at runtime via app.path().resource_dir(), with dev-mode fallback to CARGO_MANIFEST_DIR/resources/webforge

Embedded HTTP server (server.rs)

  • Hyper 1.x + hyper-util + http-body-util + tokio
  • Binds to 127.0.0.1:0 (free port chosen by OS), exposed via PortState managed state
  • Started in setup() hook, runtime leaked to keep server alive for app lifetime
  • Serves bundled Webforge with correct MIME types
  • Injects <script src="/webforge-bridge.js"></script> into editor.html before </body>
  • Routes /site/<id>/<path> to registered local site folders (same origin)
  • Shares a SiteFolders Arc<RwLock<HashMap>> between server and commands

Save/Upload interception (site_io.rs)

Two paths based on site kind:

OperationLocal siteRemote site
Save Write HTML to <folder>/<file> via fs::write with path-traversal protection (canonicalize parent, check starts_with folder) POST form to <server>/save.php via reqwest
Upload Write bytes to <folder>/uploads/<filename>, return /site/uploads/<filename> URL Multipart POST to <server>/upload.php via reqwest, parse JSON for src

Bridge shim (webforge-bridge.js)

Injected into every served editor.html. Reads site context from query params (site, kind, startUrl, folder, server).

  • Overrides Webforge.Builder.saveAjax to call invoke("save_site", {args}) instead of POSTing to save.php
  • Monkey-patches window.fetch to intercept upload.php POSTs and route to invoke("upload_site", {args})
  • Falls back to original behavior on any error
  • For local sites: sets iframe src to /site/<id>/<startUrl>
  • For remote sites: sets iframe src to /proxy/<encoded-remote-url>

Database schema (migration v2)

ALTER TABLE sites ADD COLUMN kind TEXT NOT NULL DEFAULT 'remote';
ALTER TABLE sites ADD COLUMN folder_path TEXT;
ALTER TABLE sites ADD COLUMN server_url TEXT;
ALTER TABLE sites ADD COLUMN start_page TEXT;

  • Open calls register_site_folder (binds folder to site id in server's map) then open_site (opens http://127.0.0.1:<port>/editor.html?site=<id>&kind=...&startUrl=...&folder=...&server=... in a new window)

Phase 5: Proxy, Progress, Conflict Detection

Addressed the three known limitations from Phase 4.

1. Same-origin proxy for remote sites

Replaced direct remote-URL iframe loading with a same-origin proxy so Webforge.Builder.frameDoc access works.

  • New /proxy/<percent-encoded-remote-url> route in server.rs
  • Fetches remote HTML via reqwest (30s timeout)
  • Rewrites all src, href, poster, data-src, data-href attributes to /proxy/<absolute-url>
  • Rewrites CSS url(...) references in proxied CSS files
  • Resolves relative URLs against the final (post-redirect) remote URL using the url crate
  • Skips proxying for data:, javascript:, mailto:, tel:, blob:, about:, and #anchor
  • Injects bridge shim into proxied HTML
  • Asset requests (JS/CSS/images) fetched from remote and served with correct MIME
  • Returns X-Proxied-From header with the final URL
Proxy test: 12/12 URL rewriting cases pass
  • Absolute URLs (https://cdn.example.com/lib.js) → proxied
  • Absolute paths (/css/main.css) → resolved against base origin, proxied
  • Relative paths (../images/logo.png, ./script.js) → resolved via URL::join, proxied
  • Protocol-relative (//cdn.example.com/lib.js) → prefixed with https:, proxied
  • data:, #anchor, mailto:, javascript:, tel: → left untouched

Live test against https://example.com: returned HTTP 200, links rewritten to /proxy/https%3A%2F%2Fiana.org%2F..., bridge shim injected.

2. Upload progress indicator

  • upload_site Rust command accepts AppHandle and emits upload-progress Tauri events
  • Payload: {filename, uploaded, total, percent}
  • Emits 0% at start, 100% on completion (local uploads are instant)
  • Bridge shim listens for events via window.__TAURI__.event.listen
  • Shows a fixed 4px progress bar at the bottom of the editor window
  • Bar fills with transition, hides 400ms after reaching 100%

3. File conflict detection

  • New get_file_mtime(folder_path, file) Rust command returns unix-seconds mtime
  • save_site now accepts expectedMtime field in SaveArgs
  • If set and actual mtime differs, returns SaveResult{success: false, conflict: ConflictInfo} instead of overwriting
  • Bridge shim captures mtime when a local site page loads into the iframe
  • On conflict response, shows confirm() dialog: "This file was modified on disk since you loaded it (saved at <timestamp>). Overwrite?"
  • Confirm → retries save with expectedMtime: null (force overwrite) and refreshes stored mtime
  • Cancel → save aborted, user keeps their edits
  • After any successful save, mtime is refreshed for the next cycle
Conflict detection test: 5/5 cases pass
  • Save with matching mtime → succeeds
  • Save with stale mtime (file modified externally) → conflict detected, save skipped
  • Save with fresh mtime after conflict → succeeds
  • Save with None mtime → skips check, always succeeds
  • Final file content matches the last successful save

How to Run

Prerequisites

  • Rust 1.92+ (rustup)
  • Xcode Command Line Tools (macOS) or equivalent
  • Node.js 20+ and npm

Build & run Webforge Studio

cd /Users/cal/webforge-studio
npm install
npm run tauri dev

First launch compiles ~526 Rust crates (~5 min). Subsequent launches take 5-50s.

Add a local-folder site

  1. Click the Sites tab → + Add site
  2. Select type: Local folder
  3. Enter a name, click Browse to pick a folder containing HTML files
  4. Set the start page (e.g. index.html)
  5. Click Save site, then Open on the site card
  6. Editor opens in a new window, loads the page from the local folder via the embedded server
  7. Edit → save → writes back to disk (with conflict detection)

Add a remote-server site

  1. Select type: Remote server
  2. Enter the server URL (e.g. http://localhost:8080 where save.php and upload.php live)
  3. Open → editor loads from localhost, iframe loads the remote page via the same-origin proxy
  4. Save → forwards to remote save.php

Use the Theme Builder

  1. Click the Theme Builder tab
  2. Click the drop zone or drag a folder → pick a template folder (HTML or WordPress theme)
  3. Review the classification (WP theme name detected, template count)
  4. Set a group name, click Convert templates
  5. Review generated sections with previews
  6. Click Export as .zip → save the drop-in bundle
  7. Unzip into your Webforge project: add <script src="sections.js"></script> to editor.html, copy assets/ to web root, reload
